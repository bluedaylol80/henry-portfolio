3. **언어 토글은 `/en/` 별도 페이지 방식을 추천한다.** 현재 `site/index.html`은 `data-i18n` 속성이 없는 단일 `lang="ko"` 페이지다. 채용담당자에게 링크로 바로 전달되는 용도라면 SEO보다 "받은 링크가 즉시 맞는 언어로 보이는가"가 더 중요하지만, 검색 노출까지 고려하면 정적 사전 렌더링 방식이 더 안전하다(근거는 아래 결론 참고).

**공통 패턴 (2차 출처 종합, careerfoundry/underdog 기사 기준):**
- 홈 화면에 숫자를 나열하는 사례는 드물다. 대부분 홈은 "누구인지 + 무엇을 하는지"만 담고, 정량 성과(예산 절감 25% 등)는 **개별 케이스 스터디 안에서** Challenge → Process → Outcome 구조로 제시한다.
- 세부 케이스는 대부분 **같은 사이트 내부 페이지**로 연결된다. Notion으로 직접 연결하는 개인 포트폴리오 사례는 검색에서 확인되지 않았고, Notion은 오히려 "포트폴리오 자체를 Notion으로 통째로 만드는" 저비용 대안(템플릿 갤러리)으로 주로 등장했다.
- 언어 전환 UI를 갖춘 개인 PM 포트폴리오 사례는 검색에서 발견되지 않음 🟡 — 글로벌 지원을 병행하는 PM이라도 영어 단일 언어로 사이트를 운영하는 경우가 대다수로 보인다(간접 근거, 반례 못 찾음).

## 언어 토글 결론
| 방식 | SEO | `lang` 속성 | 유지비용 | 링크 공유 시 |
|---|---|---|---|---|
| `data-i18n` + JSON 사전(클라이언트 전환) | 취약. 크롤러는 최초 셸(기본 언어) 하나만 보고, 두 번째 언어는 고유 URL이 없어 색인 대상이 아예 없음 | 전환 후에도 `<html lang>` 갱신을 코드가 직접 처리해야 함(누락 흔함) | 낮음(파일 1개) | 받은 사람이 처음 보는 언어가 마지막 저장값(localStorage) 의존 → 다른 사람에게 전달 시 의도와 다른 언어로 보일 수 있음 |
| 언어별 별도 페이지(`/en/`, `/ko/`) + `hreflang` | 각 언어가 고유 URL·고유 정적 HTML을 가져 검색 엔진이 정상 색인·언어별로 노출 | 페이지별로 고정, 누락 위험 없음 | 콘텐츠 이중 관리 필요 | 채용담당자가 받은 링크가 항상 같은 언어로 고정 노출 — 회사 리크루터에게 `/en/` 링크를 보내면 100% 영어로 보장됨 |

**추천: 별도 페이지(`/en/index.html`) + `hreflang` 상호 링크.** 근거: 정적 사이트의 검증된 다국어 SEO 표준 구성은 "언어별 사전 렌더링 HTML + 양방향 hreflang"이며, 클라이언트 전환 방식은 크롤러에 언어가 하나만 보이는 구조적 한계가 있다. 이 사이트는 검색 유입보다 "링크로 직접 전달"이 주 용도이지만, 그 경우에도 별도 페이지 방식이 더 안전하다. 리크루터에게 영어 링크(`/en/`)를 보내면 상대가 어떤 브라우저 설정·로컬스토리지 상태든 항상 영어로 열리기 때문이다(data-i18n 방식은 이전 방문자의 저장된 언어값에 좌우될 수 있음). `lang` 속성은 페이지별로 고정해 스크린리더·번역기 오작동을 막는다.
- localStorage 언어 기억은 "같은 사람이 재방문할 때"의 편의 기능으로만 보조적으로 유지하고, 최초 판단 기준(채용담당자에게 보낼 링크)은 URL 자체로 고정할 것.

## Notion 연결 결론
**장점:** 무료, 코딩 불필요, 갤러리/리스트/보드 등 다양한 뷰, Figma·동영상·코드블록 임베드 가능.
**단점:**
- 로딩 지연: Notion은 내부 데이터베이스 엔진을 브라우저에서 그대로 구동해 초기 로딩이 무겁다. 채용담당자가 링크 클릭 후 반응하는 시간은 매우 짧다는 것이 업계 통설(🟡 구체 초 단위 수치는 출처마다 다름, 정확한 원자료 확인 못함).
- 커스터마이징 제한: 폰트·색상·기본 구조를 크게 벗어나기 어려워 사이트 전체의 브랜드 톤과 이질감이 생기기 쉬움.
- 비공개 처리 불가: 페이지 일부만 비공개로 감추는 기본 기능이 없어 민감한 프로젝트 정보 노출 위험.
- 모바일: 명시적 데이터는 못 찾음 🟡 — 다만 로딩 지연 문제는 모바일에서 더 두드러질 것으로 추정(간접 근거).
- 링크 표기 관례: 업계 표준화된 라벨("과정 보기" 등)은 확인 못함 🟡. 다만 외부로 이탈시키는 링크는 새 탭으로 열고, 아이콘(예: 외부링크 화살표)으로 "이 사이트를 떠난다"는 신호를 주는 것이 일반적 UX 관례.

**결론:** 이 포트폴리오처럼 링크 하나로 전달되는 채용 목적 사이트에서는 케이스 스터디를 Notion 등 외부로 빼지 말고 **내부 페이지로 유지**하는 편이 안전하다. Notion은 브랜드 일관성·로딩 속도·비공개 제어가 필요한 채용용 포트폴리오보다는, 빠르게 만들고 버리는 초안이나 방대한 프로젝트 아카이브(관심 있으면 더 볼 수 있는 "심화 자료" 성격)에 적합하다.

## 이 사이트에 바로 적용할 체크리스트
1. 현재 `site/index.html`은 `lang="ko"` 단일 언어, `data-i18n` 없음 — 영어 지원 시작 전에 방식(별도 페이지 vs 클라이언트 전환)부터 확정할 것.
2. 영어판은 `/en/index.html`로 별도 정적 페이지 생성(클라이언트 사전 전환 방식 채택하지 않기).
3. 한국어/영어 페이지 `<head>`에 서로를 가리키는 `hreflang="ko"`/`hreflang="en"` + `x-default` 태그 추가.
4. 각 페이지 `<html lang>`을 해당 언어로 고정(전환 스크립트로 갱신하는 방식 지양).
5. 리크루터에게 보낼 기본 공유 링크는 지원하는 회사 국적에 맞춰 `/` 또는 `/en/`을 명시적으로 고르게 안내(자동 감지에 의존하지 않기).
6. 첫 화면에 이름·현재 직함·핵심 도메인 한 줄 + 대표 프로젝트 3~5개 카드 미리보기 구조 유지(현재 구조와 정합적인지 확인).
7. 홈 화면에는 숫자를 나열하지 말고, 프로젝트 카드 클릭 후 진입하는 개별 케이스 안에서 Challenge → Process → Outcome 흐름으로 정량 성과 배치.
8. 케이스 스터디는 Notion 등 외부로 빼지 말고 계속 내부 페이지(현재처럼 단일 사이트 내)로 유지.
9. 만약 심화 자료(원본 리서치 문서, 방대한 부록)를 별도로 공유할 일이 생기면 그때만 외부 링크를 쓰고, 새 탭+외부링크 아이콘으로 이탈 신호를 명시.
10. 언어 토글 UI 자체(버튼 위치·라벨)는 검색으로 확인된 검증 사례가 없었으므로 🟡 — 별도 UX 리서치나 A/B 없이 임의로 화려하게 만들지 말고 헤더 우측 상단 텍스트 토글(KO/EN) 정도의 관례적 형태를 권장.
